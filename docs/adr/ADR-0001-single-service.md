# ADR-0001 — خدمة خلفية واحدة تخدم الـSPA من المنصّة نفسها

> حالة القرار: **مقبول** — توثيق قرار قائم فعلًا في الشيفرة (لا قرار جديد).
> التاريخ: مكتوب في جولة التنظيم `chore/repo-cleanup-and-architecture`؛ القرار نفسه أقدم من السجل.

## السياق

أُلارا منصّة أكاديمية واحدة (لا SaaS متعدد المنتجات)، عربية-أولًا، بنشر Vercel + Neon،
وفريق صغير + وكلاء برمجة يعملون بجولات مرقّمة مع بوابات CI صارمة.

## القرار (كما هو مطبَّق)

- تطبيق Express واحد (`backend/src/app.ts`) يقدّم واجهات `/api/v1/*` **ويخدم** مخرجات بناء
  الـSPA (`frontend/dist`) في المنصّة نفسها؛ نشر Vercel عبر دالة serverless واحدة
  (`api/index.ts` → `createApp()`) مع إعادة كتابة `/api/(.*)` وإسقاط SPA في `vercel.json`
  (دالة `maxDuration 60`، منطقة `fra1`، cron يومي `0 3 * * *`).
- عقد الـAPI مصدره الشيفرة ويولَّد إلى `docs/api/openapi.json` (`npm run api:openapi`) —
  المقاس عند الفحص: 315 مسارًا / 388 عملية.

## البدائل المرفوضة

- **استضافة SPA منفصلة (CDN ثابت + API مستقل):** يجزّف نقطة النشر إلى مشروعين ويعرّض
  CORS وطابق الإصدارات بين وجهتين — مقابل لا شيء لمنصة أحادية النطاق.
- **تقسيم microservices:** حجم الفريق وبوابات «صفر انحلال» تجعل توزيع الخدمة كلفة صرفة؛
  حدود الوحدات الداخلية (`src/modules/`) تكفي للحوكمة.

## العواقب

- نشر واحد ذرّي (واجهة + خلفية معًا) — بسيط للرجوع والتحقق (`/api/v1/health` يعرض SHA).
- سقف وظيفة serverless (60 ثانية) هو حد المعمارية، لا حد التطبيق — المهام الثقيلة (بذر،
  نسخ احتياطي) سكربتات محلية/CI لا دوال HTTP.
- CSP مثبّتة بصمات sha256 في `vercel.json` و`backend/src/app.ts` — تغيير `index.html`
  يلزم تحديث البصمة (`check-csp-hash.sh` بوابة).
