# النشر والتشغيل اليومي

> الغرض: كيف تُشحن أُلارا (ويب + تطبيق، مستودع واحد، فرع واحد `main`)
> وما الذي يفعّل النشر أين، والمتغيرات وcron وعمل المشغّل اليومي.
> الشيفرة مصدر الحقيقة: `vercel.json` و`.github/workflows/*.yml`.

## 1. ماذا يفعّل ماذا (push إلى `main`)

| التغيير | Vercel (الويب) | GitHub Actions | EAS |
|---|---|---|---|
| `backend/**` | ✅ نشر (workflow `deploy.yml` بأسراره الثلاثة، أو `vercel deploy` يدويًا) | CI + **deploy-smoke** (ينتظر `buildId == SHA` ثم صحة + 12 دخولًا + لوحة + مقارنة OpenAPI حي/مُلتزَم additive؛ الفشل يفتح issue) | — |
| `frontend/**`, `shared/**` | ✅ نشر | CI | — |
| `apps/mobile/**` أو `shared/**` | ❌ أبدًا (`.vercelignore` يستثني التطبيق) | **Mobile**: بوابات (typecheck · lint · contract-check · export · bundle) + **android-smoke** + **Android APK** | EAS Update لقناتي `production`/`preview` — **خامل** حتى خطوات إعادة التفعيل (§5) |
| تغيير native (تبعية/إضافة/`app.config.ts`/أصول) | ❌ | نفس البوابات + APK جديد | — (EAS Build مُحال — لا بناء native عبر EAS) |
| `docs/**`, `*.md` | ❌ | CI فقط | — |

## 2. المنصة (Vercel + Neon) — الإعداد المنجز

- `api/index.ts` محوّل Vercel؛ `vercel.json`: بناء (prisma generate +
  بناء الواجهة والخلفية)، rewrites (SPA + `/api`)، رؤوس أمنية (CSP
  ببصمة bootstrap السمة، HSTS، …)، وcron (§4).
- **الترحيلات جزء من بناء Vercel (المسار الحقيقي)**: `buildCommand` في
  `vercel.json` هو `bash scripts/vercel-build.sh` — منطق البناء نفسه
  (بوابة `VERCEL_ENV=production` ثم `prisma:deploy` ثم توليد العميل
  وبناء الواجهة والخلفية والتحقق من `backend/dist/app.js`) انتقل إلى
  السكربت في 2026-11-23: السلسلة المضمّنة بلغت 268 حرفًا بينما مخطط
  Vercel يسقّف `buildCommand` عند **256**، ففشلت كل نشرات preview منذ
  إدخال بوابة الترحيل بخطأ تحقق المخطط **قبل** أي بناء («The
  `vercel.json` schema validation failed … `buildCommand` should NOT be
  longer than 256 characters»). السكربت يعيد استخدام نفس العقد،
  و`.vercelignore` يعيد تضمينه صراحةً.
- **عقد قفل الترحيل (سكربت `backend/scripts/migrate-deploy.mjs`)**:
  المرشحات للترحيل اتصالات **مباشرة فقط** — `DIRECT_DATABASE_URL`، أو
  المشتق بتجريد `-pooler` من `DATABASE_URL`، أو `DATABASE_URL` نفسه إن
  كان مباشرًا. **لا مسار احتياطي عبر الـpooler إطلاقًا**: PgBouncer في
  وضع transaction pooling لا يضمن ثبات جلسة PostgreSQL طوال القفل
  (وثائق PgBouncer)، و`connection_limit=1` لا يثبت شيئًا عن هوية الجلسة
  الخادمية — فعندما لا يصل أي مرشح مباشر يفشل السكربت بأمان برسالة
  تشخيص واضحة بدل الترحيل بلا حماية. القفل نفسه
  `pg_advisory_xact_lock` (على مستوى **المعاملة**) داخل معاملة Prisma
  تفاعلية واحدة تُثبِّت اتصالًا واحدًا للجلسة كلها: القفل والإطلاق
  وجميع خطوات الترحيل تجري على جلسة واحدة مضمونة، ويُحرَّر القفل حتمًا
  عند COMMIT/ROLLBACK أو بموت العملية (لا قفل عالق أبدًا — مُثبَت
  بحزام `tests/integration/migrate-lock.test.ts`). عقد Prisma 5.22
  مُتحقَّق تجريبيًا: `SET LOCAL` عبر واجهة التنفيذ `$executeRawUnsafe`،
  واستعلامات `SELECT` (اكتساب القفل، `pg_locks`) عبر واجهة النتائج
  `$queryRawUnsafe` — الشكل العاري `SELECT pg_advisory_xact_lock(…)`
  يرفضه Prisma («Failed to deserialize column of type 'void'») فيركب
  القفل سطرًا حاملًا مطبوعًا؛ وللـ`SET` القديم عبر واجهة التنفيذ على
  استعلام SELECT كان يُرجع عدد الصفوف ويُخفي نتائجها (لا يمكن ملاحظة
  نجاح القفل قط). بعد انتهاء الترحيل يعيد السكربت التحقق من خلال
  `pg_locks` أن القفل ظل محوزًا طوال التشغيل — لا يُعلَن نجاح ترحيل
  لم يكن القفل مملوكًا فعليًا خلاله، وخطأ انتظار القفل (300 ثانية)
  يفشل بصوت عالٍ ولا يُبتلع أبدًا.
- **عازل Vercel المزدوج**: بوابة `VERCEL_ENV=production` في سكربت
  البناء، **وأيضًا** داخل `migrate-deploy.mjs` نفسه (يرفض أي بيئة
  Vercel غير إنتاجية حتى لو أعاد أحدهم توصيل البوابة)، ومتغير
  `DATABASE_URL` في Vercel منفصل بين preview وproduction (قاعدتا Neon
  مختلفتان — مُتحقَّق عبر API المنصة)، فبناءات preview لا تستطيع لمس
  قاعدة الإنتاج ترحيلًا قط. البوابة `VERCEL_ENV=production` **فقط** —
  بناءات preview لا تُرحِّل الإنتاج أبدًا؛ مسار CLI في `deploy.yml`
  وتكامل Git في Vercel يركبان نفس `buildCommand`؛ والنشر idempotent
  (إعادة `prisma migrate deploy` على قاعدة محدّثة = no-op).
- **Neon cold start**: الويب دائم الاستيقاظ على Vercel؛ القاعدة (Neon
  مجانية) تصفر الحساب بعد الخمول — أول طلب يدفع استيقاظًا أقل من ثانية،
  وسكربت `backend/scripts/migrate-deploy.mjs` يعيد المحاولة حتى استيقاظ Neon.
- أول طلب بعد نشر جديد: `deploy-smoke` يستقصي `GET /api/v1/status` حتى
  يطابق `buildId` رأس `main` (حتى 20 دقيقة) — ويسير حزام انحراف المخطط:
  `GET /colleges` + `auth/me` + `me/permissions` + `catalog/*`.
- **حادثة 2026-11-23 (انحراف مخطط الإنتاج)**: الترحيلات 0003–0005 لم
  تصل قاعدة الإنتاج قط (لا مسار نشر كان يُنفّذ الترحيل) فخدم الإنتاج
  أخطاء 500 — `GET /colleges` (P2022: عمود `Faculty.orgUnitId`) و
  `GET /auth/me` (P2022 عبر includes الكلية) و`/catalog/*` (P2021:
  جداول r352 غائبة) و`/me/permissions` (P2021: `UnitCapabilityGrant`).
  العلاج: بروفة على نسخة معزولة، تطبيق 0003–0005 + بذر كتالوجات r352،
  ثم تثبيت المسار أعلاه + حزام الدخان + حزام الانحدار
  `r352-production-regression.test.ts`.
- **تقارب كتالوجات المرجع في الإنتاج**: `npm run seed:r352 -w backend`
  (idempotent، إضافي فقط) — المشغّل الجراحي لقواعد الإنتاج المؤسّسة.
  البذرة الكاملة `prisma/seed.ts` إنشاء-فقط (r180): القاعدة المؤسَّسة
  (بها مستخدمون) تُتخطى بالكامل باستثناء حسابات @test.ly الموثّقة
  وكتالوجات r352 الإضافية وبذور الترحيل الحاجزة — لكن تشغيلها في
  النشر يبقى مسؤولية مشغّل واعية، والمشغّل الجراحي أعلاه هو المسار
  الموصى به.
- **بقايا قاعدة الإنتاج (صادقة — ليست نظيفة)**: 14 جدولًا يتيمًا من
  السلالة السابقة للـsquash (MailOutbox، MailSuppression،
  NotificationPreference، StudentDocument، AiInstitutionQuota،
  EmailVerificationToken، FieldValue، ImportJob، ImportMappingProfile،
  ImportRow، ImportUpload، InstitutionFieldDefinition، RateLimitHit،
  TickRun) + أعمدة/فهارس شاردة (مثل `AiTelemetry.provider` وبعض فهارس
  trgm/title) — خاملة بالنسبة للتطبيق الحالي (لا نموذج Prisma يشير
  إليها)، أُبقيت لتجنّب تدمير بيانات حيّة؛ ترحيل تنظيف مستقبلي بموافقة
  المالك قد يُسقطها.

### 3.1 — حالة البريد الحية (r344، مقاسة لا مزعومة)

النقل يعمل فعليًا على الإنتاج منذ r344: `MAIL_PROVIDER=resend` +
`MAIL_API_KEY` + `MAIL_FROM=«أُلارا <onboarding@resend.dev>»` +
`APP_ORIGIN=https://ulara.vercel.app` (all production+preview, encrypted).
تم قبول رسالة إرسال حية من مفتاح resend المحصور بالإرسال (`id` أُعيد
من API الرسائل) — أي أن مسار الطاقة للبريد **مشتعل**.

**الحد الصادق المتبقي**: حساب resend بلا نطاق موثّق —
`onboarding@resend.dev` يوصل إلى بريد المالك فقط
(ahmadmedo1012@gmail.com)، وأي مستلم آخر = رفض 403 من المزوّد يتكفل به
طبقة `sendMail` بصدقها المكتوب (200 عام على forgot + warn بالسجل، لا
تسريب). لتفعيل كل المستلمين: توثيق نطاق في resend.com/domains
(فعل لوحة تحكم للمالك فقط — لا يمكن للمفتاح المحصور بالإرسال إنشاء
نطاقات)، ثم قلب `MAIL_FROM` إلى `no-reply@<النطاق>` في Vercel.
القاعدة قبلها لا تنكسر: نصف إعداد = منع إقلاع، ورفض المزوّد لا يُكذب
على المستخدم أبدًا.

### 3.2 — وصفة Gemini (r351 AI-1)

مزوّد الذكاء عبر نقطة التوافق مع OpenAI لدى Google (قراءة حية من
الوثائق الرسمية 2026-11-21):

```
AI_PROVIDER=openai
AI_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
AI_MODEL=gemini-3.1-flash-lite
AI_MODELS=gemini-3.1-flash-lite,gemini-4-hydrogen
AI_API_KEY=<سر المالك — لا يوضع في أي ملف>
```

- **الوسم الصادق**: يظهر المزوّد «gemini» (لا «openai») — النقل متوافق،
  الجهة مختلفة.
- **النموذجان الموصى بهما** (من صفحة النماذج الرسمية وقت التنفيذ):
  `gemini-3.1-flash-lite` — مستقر، «أداء بمستوى الطرازات الكبيرة بجزء
  من التكلفة»، الخيار اليومي للطلبة؛ و`gemini-4-hydrogen` — نموذج
  التوافق الافتراضي في الوثائق، ذكاء أحدث بسرعة وكفاءة، كبديل أعلى.
- **السلسلة المرتّبة** (`AI_MODELS`): عند 429/503 فقط ينتقل الطلب من
  النموذج الأول إلى الثاني (إسناد النموذج لكل ردّ يبقى من ردّ المزوّد
  نفسه). فشل المفتاح (401/403) أو النموذج (404) أو الحمولة (400)
  يظهر فورًا دون إعادة محاولة على النموذج الثاني.
- **التدفق**: يُطلب `stream_options.include_usage` ويُقرأ عدّاد
  الاستخدام من الردّ فقط (غيابه = 0، لا تقدير). حقول دلتا الزائدة
  لدى Gemini (الاستدلال/التوقيعات) تُهمل ولا تصل للطالب.
- **لا تعطيل للتفكير**: نماذج Gemini 3/4 لا تسمح بإيقاف «التفكير» —
  يُستخدم المستوى الافتراضي للنموذج.

## 4. cron والوظائف اليومية

`vercel.json` ← `crons`: `0 3 * * *` يضرب `GET /api/v1/jobs/daily`
بسرّ `CRON_SECRET`. وظيفة قاعدة البيانات اليومية **واحدة**: تقليم
`LoginEvent` (180 يومًا) — مزامنة حقائق مؤسّسة العرض تقاعدت مع نظام
zu-sync (r342 t13). مع `ULARA_TEST_ACCOUNTS=1` تضيف الجولة اليومية نفسها
تمريرة ensure لحسابات العرض (§6) — **وفي الإنتاج ترفضها سياسة r352 §5
داخل الدالة نفسها (صفر كتابات: لا إعادة تفعيل ولا إعادة ضبط كلمة
لمالك العرض)، والتقرير اليومي يحمل الرفض بسببه الصادق**؛ والطلب
الفوري: `POST /api/v1/jobs/test-accounts` بسرّ الخدمة (نفس السياسة
ونفس التقرير). في النشر الطويل الأمد يعمل مجدول داخل العملية نفسها
(إقلاع + كل 24 ساعة).

## 5. قناة أندرويد المباشرة + OTA

- **APK موقَّع مباشر** (`android-apk.yml` على runners GitHub): يُبنى
  بسكربت `scripts/build-android-local.sh` ويُنشر إلى إصدار `latest`
  المتدحرج — رابط ثابت دائمًا الأحدث:
  `https://github.com/ahmadmedo1012/ulara/releases/latest/download/ulara.apk`
  مفتاح توقيع مخصّص منفصل عن مفتاح المتجر (أسرار Actions:
  `ANDROID_KEYSTORE_B64/PASSWORD/KEY_ALIAS/KEY_PASSWORD`)؛ التوقيع
  المستقر = تحديث في مكانه بلا إزالة تثبيت. صفحة `/app` هي مصدر
  التنزيل المواجه للتطبيق (تخدمها الخلفية `updateUrl`).
- **مسارا البناء المنفصلان (R336 C)**: المسار انقسم إلى مسارَين —
  (أ) **مسار QA** (`qa-apk`): يبني على كل push مؤهِّل APK بتوقيع
  التصحيح (`ALLOW_DEBUG_KEYSTORE=1` — مسار السكربت الموثّق نفسه) بلا
  أي أسرار توقيع، وينشره **كناتج workflow فقط** (30 يومًا) — لا يلمس
  إصدار `latest` أبدًا؛ (ب) **مسار الإصدار** (`release-apk`): يفحص
  الأسرار الأربعة **أولًا قبل أي تنزيل SDK**، وعند غيابها يتخطّى
  بإشعار واضح (مانع خارجي — يوثَّق في ملخص الوظيفة) بدل الفشل الأحمر
  بعد نصف ساعة إعداد (فشل التشغيل 43364410025)، وعند وجودها يتحقق من
  المخزن بـ `keytool` قبل Gradle، ويثبّت بصمة شهادة التوقيع (مطابقة
  مخزن المفاتيح + السر الاختياري `ANDROID_KEY_CERT_SHA256` عند
  توفيره)، وينشر `SHA256SUMS.txt` كأصل في الإصدار، ويرفع سجلات
  البناء عند الفشل. المشغّل اليدوي يقبل مدخل `lane`:
  `qa`/`release`/`both`.
- **OTA** (`expo-updates`, سياسة fingerprint): تغييرات JS تصل كل بناء
  مطابق للبصمة؛ التغيير native يغيّر البصمة ⇒ يلزم بناء جديد مرة ثم
  تجري التحديثات فوقه. **القناة موصولة لكن خاملة**: مشروع EAS الجديد
  لم يُنشأ بعد (`eas init` معلّق) و`EXPO_TOKEN` غير مضبوط. خطوتا
  المالك (~5 دقائق): (1) `npx eas-cli init` من `apps/mobile` وتثبيت
  المعرف الحقيقي في `app.config.ts`؛ (2) إنشاء token في expo.dev ←
  سر Actions `EXPO_TOKEN`. التفصيل: [mobile.md](mobile.md). EAS تبقى
  قناة OTA (JS) فقط — عقد المالك المُلزم: البناء native عبر GitHub
  Actions حصرًا و`eas build` مُحال.
- **حقيقة التثبيتات المتقطعة**: البناء من مشروع EAS القديم لا يستقبل
  تحديثات المشروع الجديد (بصمة مختلفة) — طريق ترقيته: إزالة تثبيت
  واحدة ثم تثبيت APK من `/app`؛ بعدها التحديثات في مكانها. الحد الأدنى
  `MIN_APP_VERSION` هو الحارس الشامل لأي متخلّف.

## 6. التشغيل اليومي وحسابات العرض

**فحص ما قبل العرض (5 دقائق):**

```bash
curl -s https://ulara.vercel.app/api/v1/health   # ok:true وbuildId يطابق main
```

افتح `/` (الوضعان فاتح/داكن) ثم سجّل الدخول بحساب طالب.

**حسابات الاختبار** (المصدر الوحيد:
`backend/src/modules/auth/test-accounts.data.ts` — 12 حسابًا، النطاق
`@test.ly` علامة الديمو في المخطط، الكلمة `12345678` معلَنة عمدًا
للتطوير):

| الدور | البريد |
|---|---|
| طالب / طالب ثانٍ (عزل) | `student@` / `student2@test.ly` |
| أستاذ / أستاذ ثانٍ | `teacher@` / `teacher2@test.ly` |
| رئيس قسم / عميد / نائب عميد | `head@` / `dean@` / `vicedean@test.ly` |
| مسجل عام / مسجل كلية / مسجل ثانٍ | `registrar@` / `faculty@` / `admin2@test.ly` |
| أخصائي جودة | `quality@test.ly` |
| مالك المنصة | `owner@test.ly` |

- **إنقاذ الدخول ذاتي البنيوية (بيئات غير الإنتاج فقط)**: مع
  `ULARA_TEST_ACCOUNTS=1` تعيد تمريرة ensure (الإقلاع + cron اليومي +
  `POST /jobs/test-accounts`) كل حساب إلى كلمة العرض. اليدوي:
  `npm run db:ensure-test-accounts`.
- **سياسة الإنتاج (r352 §5 — إغلاق نهائي)**: تمريرة ensure نفسها
  ترفض الاشتغال في تشغيلية إنتاجية (يُعرّفها `NODE_ENV=production` أو
  أي نشر Vercel غير `preview`/`development`): **مالك العرض
  (`owner@test.ly`) لا يُنشأ ولا يُفعّل ولا يُعاد ضبط كلمته أبدًا —
  لا راية تتجاوز ذلك**، وحسابات العرض غير المالك ترفض افتراضاً ولا
  تبقى إلا بقرار مشغّل صريح (`ULARA_TEST_ACCOUNTS_PRODUCTION_DEMO=1`)
  لأنها محصورة بمؤسسات العرض المعيّنة ومساراتها الإدارية مقيّدة
  بمؤسسة متحقّق منها من قاعدة البيانات (إغلاق r352 §3). التطوير
  المحلي وقواعد الاختبار المعزولة وبيئات preview تحتفظ بالطقم
  الكامل (المالك مضمّناً). حزام الوحدات:
  `backend/tests/modules/test-accounts-production-policy.test.ts`.
- **فحص دخان الإنتاج بلا اعتماد كلمة معلَنة (r352 §5)**: فحص ما بعد
  النشر (`.github/workflows/deploy-smoke.yml`) لم يعد يسجّل دخول أي
  حساب `@test.ly` على الإنتاج: مسارات الإنتاج حية بلا اعتمادات
  (الصحة + الكليات العامة + حزام SQL للكتالوجات/الرصيد قراءةً فقط
  + مقارنة OpenAPI)، ومصفوفة الرحلات المصادَقة كاملة (12 دخولاً
  بضمنها مالك العرض + اختيار المؤسسة + حزام r352 + إثبات المتصفح)
  انتقلت إلى **بيئة معزولة تُبذَر وتُبنى في السكربت نفسها** — تغطية
  سلوك المالك (§5.6) بلا اعتماد إنتاج واحد.
- **تدوير كلمة قبل عرض/إنتاج حقيقي**:
  `npm run db:rotate-password -- --email <الحساب> --new-password-env NEW_PASSWORD --yes`
  (لا تعِد بذر الإنتاج أبدًا)؛ حساب باسمك:
  `npm run db:provision-owner -- --email <بريدك> --yes --suspend-demo-owner`.
- **سردية العرض** (مختصرة): عام ← دخول طالب (لوحة/مقرر/مشغّل محاضرة/
  مكتبة/مساعد) ← أستاذ (تكليف ودرجة) ← مسجل (كلية←قسم←مقرر) ← مالك
  (لوحة/حاكمية) ← **العزل**: ادخل `student2` وحاول فتح ملف المؤسسة
  الأولى ⇒ 403/404 بلا إفصاح.
- **حدود صادقة** (قلها إن سُئلت): الذكاء وضع محلي صادق أو مزوّد خارجي
  بتدهور معلَن؛ نسب الاستلال محاكاة؛ مؤسسة عرض واحدة + مؤسسة عزل؛
  النطاق طيار 5–10 طلبة.

### 6.1 — دليل المشغّل: تأمين هوية مالك العرض على الإنتاج (r352 §5)

**الحالة المسجّلة (قراءة فقط — لم يتصل هذا المسار بقاعدة الإنتاج ولا
عدّلها):** هوية `owner@test.ly` موجودة على قاعدة الإنتاج الحالية،
نشطة، بكلمة العرض المعلَنة، ودورها `OWNER` (هوية ملك المنصة) بلا
عضوية مؤسسة. إصلاح الكود وحده لا يؤمّن حساباً موجوداً فعلاً — لذلك
هذا الإجراء **مانع إصدار** حتى تنفيذه وتحقّق القراءة فقط منه.

**الإجراء (يفعله المالك/المشغّل بنفسه — بترخيص من المالك):**

1. **إبطال الجلسات الحالية** (الترتيب مقصود — كل خطوة تالية تُبطل ما
   قبلها من جديد):
   ```bash
   # 1) رفع tokenVersion يقتل التجديد: كل JWT صادر يرفض عند /auth/refresh
   #    (الوصول الحامل صلاحية قصيرة يبقى حتى انتهائه فقط).
   psql "$ULARA_DB_URL" -c "UPDATE \"User\" SET \"tokenVersion\" = \"tokenVersion\" + 1 WHERE email = 'owner@test.ly';"
   # 2) تعطيل الحساب فوراً (يحجب الدخول والتجديد معاً):
   psql "$ULARA_DB_URL" -c "UPDATE \"User\" SET \"isActive\" = false WHERE email = 'owner@test.ly';"
   ```
   > من يعمل بواجهة OWNER الشرعية (المالك بنفسه) يفعّل حساباً حقيقياً
   > باسمه: `npm run db:provision-owner -- --email <بريدك> --yes
   > --suspend-demo-owner` — السكربت نفسه يوقف هوية الديمو مع تنفيذ
   > الترقية (مسار `scripts/provision-owner.mjs` الموثّق).
2. **التحقق بالقراءة فقط بعد التنفيذ** (هذا هو دليل الإغلاق):
   ```bash
   psql "$ULARA_DB_URL" -t -c "SELECT email, role, \"isActive\", \"failedLoginCount\" FROM \"User\" WHERE email = 'owner@test.ly';"
   # المتوقع: isActive = false (أو الصف غائب تماماً إن اختار المالك الحذف)
   curl -s https://ulara.vercel.app/api/v1/auth/login -X POST -H 'Content-Type: application/json' \
     -d '{"email":"owner@test.ly","password":"12345678"}' -o /dev/null -w '%{http_code}\n'
   # المتوقع: 401/403 (وليس 200 بحال)
   ```
   > لا تُطبع الكلمة في سجلات Actions ولا تُصدّر نتائج psql إلى
   > مستودع عام — الكلمة نفسها معلَنة في المستودع عمداً للتطوير، لكن
   > **الاعتماد عليها على الإنتاج هو الخلل** الذي يغلقه هذا الإجراء.
3. **مانع إعادة التنشيط الصامت (مضمّن بالكود بعد r352 §5):** كل مسارات
   ensure (الإقلاع بـ`ULARA_TEST_ACCOUNTS=1`، cron اليومي،
   `POST /jobs/test-accounts`، `db:seed`، سكربت المشغّل، وبذر
   `owner@test.ly` داخل البذرة نفسها) ترفض الاشتغال على تشغيلية
   إنتاجية — لا راية تتجاوز رفض المالك. الحزام:
   `backend/tests/modules/test-accounts-production-policy.test.ts`
   (12 اختباراً).
4. **الحالة في تقرير الإصدار:** يبقى بند **مانع إصدار — إجراء مشغّل
   الإنتاج** حتى يتحقق المشغّل/المالك بالقراءة فقط من الخطوة 2
   ويسجّل النتيجة (لا يُغلق البند بالكود وحده ولا بادعاء دون تحقق).

**ما لم يُفعل بعد (لا تدّعِه):** لم ينفّذ أي وكيل هذا الإجراء على
الإنتاج — العمل على الإنتاج في هذه الجولة كان **قراءة فقط**
(رصيد الترحيلات/الجداول/الكتالوجات/حالة الهوية). التنفيذ بيد المالك.

## 7. التخزين والملفات (حدود المضيف الصادقة)

Vercel Functions تسقّف جسم الطلب/الاستجابة عند **4.5 MB** (جبلان
الاتجاهين، خطأ 413 من المنصة قبل أن يرى التطبيق بايتًا) — لذا سقف PDF
المعلَن **4 MiB على Vercel** و**20 MiB عند الاستضافة الذاتية**
(`lib/pdf-limits.ts`)؛ القيمة الحية في `/status` → `maxPdfUploadBytes`
وتفرضها الأسطح الثلاثة. GET ملف أكبر من سقف المضيف يرد 413 عربيًا
يوجّه للعارض داخل التطبيق (RANGE يقطّع تحت الجدار). الفيديو عبر رفع
موقَّع مباشر إلى S3 (`POST /uploads/presign`) لا يمر بدالة — يلزم
`STORAGE_DRIVER=s3`. فتح 20 MiB+ على Vercel: ضبط `S3_*` ثم مدّ التوقيع
المسبق لمساحات PDF (خطة لاحقة).

## 8. النسخ الاحتياطي والاستعادة

```bash
npm run db:backup    # نسخة إلى backups/ مع sha256
npm run db:restore -- --url-env <TARGET> --file backups/<ملف>   # إلى قاعدة عزل فقط
npm run db:verify    # جداول/ترحيلات/عدّ صفوف مقابل قاعدة مرجعية
```

- الاستعادة إلى قاعدة حيّة مرفوضة افتراضيًا (`--confirm-live-restore`
  هو التجاوز الواعي للطوارئ).
- **الخطوة المتبقية على المالك**: نقل ملفات النسخ خارج الخادم — نسخة
  على نفس صندوق القاعدة ليست نسخة احتياطية (`backups/` مهمل في git).
- تدريبات موثقة: آخر جولة كاملة (نسخ 294KB/241ms ← استعادة في قاعدة
  عزل ← `db:verify` PASS ← خلفية ثانية على القاعدة المستعادة ← إسقاط
  القاعدة) — تُسجَّل الجولات في `docs/ops/LEDGER.md`.

## 9. بوابة الحد الأدنى للإصدار + صفحة التوزيع

- `GET /api/v1/status` → `{ minAppVersion, updateUrl }`؛ التطبيق يقارن
  semver عند الإقلاع والعودة: أدنى من الحد ⇒ شاشة تحديث حاجزة مع رابط
  `/app`. غير مضبوط ⇒ لا بوابة. رفعه: متغيرات بيئة Vercel.
- `/app`: APK المباشر (إصدار `latest`)، تاريخ الإصدارات + بصمات، «ما
  الجديد»، حالة iOS. تخدمها الخلفية `updateUrl`.
- **تحديث داخل التطبيق**: فحص صامت عند الإقلاع (`ON_LOAD`) ← تنزيل ←
  toast «تحديث جاهز — أعد التشغيل». خامل حتى إعادة تفعيل OTA (§5)؛
  Telemetry التحديث يحمل `updateId` فيظهر في صندوق المالك أي تحديثٍ
  جاء منه انهيار.
